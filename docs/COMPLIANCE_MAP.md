# Compliance checklist: what the code covers

This maps the *Niveloft compliance checklist* (5 October 2026) to the code. It's an engineering note, not legal advice and not a compliance claim: the checklist itself says applicability and implementation are unverified, and an enrolled Indian technology advocate should assess the finished product. Nothing here should be advertised as "compliant".

**Supported by the code** means something in this repository helps with the item, and where it lives. **Not in the code** means it needs a decision, a document, a provider setting or a person, or hasn't been built.

| Checklist item | Supported by the code | Not in the code |
| --- | --- | --- |
| **1 Operator** | `VITE_OPERATOR_NAME` and `VITE_CONTACT_EMAIL` fill the legal pages and footer. | Who the operator actually is, entity filings, registrations. |
| **2 Personal data map** | The data is in a few places: accounts (including when each person last caught up on Today), projects, tasks, comments (and the @mentions in them, which notify the people named), evidence files (`backend/data/uploads`), contact messages, sign-up sources, form counts, Arena votes, sign-in sessions (device, a /24 or /48 network, times), the audit log (actions and outcomes, no content), project documents and their passages, corrections to Flurry's answers (verdict, kinds of mistake, the correction, the question and answer, the model and lookups; no name shown; 180 days), the Delivery page's step counts (words from a fixed list only; 180 days) and forecast trial records (numbers only) (`backend/src/main/resources/db/migration`). Analytics only with consent, with ids, query strings and tokens redacted. | The written inventory (purpose, recipients, countries, retention per category) and the controller/processor decision. |
| **3 DPDP** | A plain-language privacy page; consent for analytics; self-service access (a JSON copy of your data), correction (profile) and erasure (delete account) in Settings; sign-up is for people aged 18 or over; breach-notice steps in `docs/launch/RUNBOOKS.md`. | Consent records, nomination, a grievance contact, and the legal review of notice wording and commencement dates. |
| **4 CERT-In** | Server logs, an uptime check (`.github/workflows/uptime.yml`), an audit log kept at least 180 days, UTC timestamps, and the six-hour reporting steps in `docs/launch/RUNBOOKS.md`. | 180-day retention of the host's logs in India, clock synchronisation (NTP), the designated contact and drills. These are hosting and process settings. |
| **5 Intermediary** | — | The classification assessment, published rules, grievance officer and complaint/order processes. |
| **6 Security controls** | Every project endpoint checks membership on the server (`@projectAccess.isMember`, role checks in `security/ProjectAccess.java`); approval only through a review by an authorised reviewer, also on direct API calls; evidence files only to project members, served with `nosniff`; the build refuses to finish if the bundle holds a secret (`frontend/tools/seo.ts`); API keys stay on the backend; rate limits, spending caps; backup and restore scripts with a restore test; server-side sessions you can end; an audit log; an upload allowlist with signature checks and optional ClamAV scanning; a production settings guard; emergency switches; CI with a secret scan and dependency audit. | MFA for users (not built), a security assessment, staff-access records, dependency patching as a routine. Where each launch check stands: `docs/launch/LAUNCH_READINESS.md`. |
| **7 Flurry and forecasts** | Flurry's header always says what's answering (*AI model on · model*, *in this browser*, or *No AI model · built-in answers*); the AI's context is built on the server from records the signed-in user can see; permissions are enforced by the normal endpoints, not by the model; every change is previewed, confirmed and undoable; Flurry never approves, assigns or changes deadlines on its own; its tools read only the project being asked about, include nothing that approves, assigns, reschedules or deletes, and every answer lists what it looked up, keeping "found nothing" apart from "couldn't be read"; the natural voice (ElevenLabs) is off by default, keeps its key on the server and is named in the privacy policy; the task-history export for forecast training is owners and managers only and holds no names or written text; Flurry's evidence links open only records the reader may see; project documents reach Flurry only once an owner or manager approves them, and drafts are never searched; corrections are shown to owners and managers without names; an answer can be stopped, and the server then stops the provider; a trained forecast model only runs beside Niveloft's forecast, with both forecasts recorded and a switch to stop the trial; forecasts show their assumptions, data quality, uncertainty and calibration; people are never ranked or scored. | Provider terms (retention, training, countries) for whichever AI provider you configure, and for ElevenLabs if you turn the voice on; written AI disclosures in the terms; the licence of any public dataset or model you use for training; and the separate assessment before any worker evaluation. |
| **8 Consumer and billing** | No prices, checkout or subscriptions exist in the app, and the site shows no invented customers, reviews or urgency. | Everything here, if paid plans are added. |
| **9 Payments and taxes** | No card data is handled. | Everything here, if payments are added. |
| **10 IP and contracts** | Fonts, libraries and the 3D world are open-licensed or built from code; `THIRD_PARTY_NOTICES.md` lists them. Flurry's artwork is the image you supplied. | Trademark clearance for *Niveloft* and *Flurry*, contributor IP assignments, a customer-content licence, a DPA, executed terms. |
| **11 International** | — | Market-by-market screening before launch. |
| **12 Evidence** | Task history, review decisions and submission versions are kept; contact messages are logged. | The obligation register, legal holds, insurance, and the advocate. |

The checklist's suggested **release blockers** map like this: cross-workspace access and Flurry retrieving content outside the signed-in user's permissions are guarded by server-side membership checks on every project and AI endpoint (tested in the backend tests and the mock API); exposed privileged credentials are guarded by the build's secret check and by keeping keys on the backend; public private files are guarded by member-only evidence downloads. None of this replaces the independent security assessment the checklist recommends.
